# 类似 RAG 项目的公开简历：精选写法与本项目对照

检索日期：2026-10-12。以下均已打开作者个人网站上的简历正文，按场景清楚、个人动作明确、结果具体、与研发知识库相关这四点筛选。这里的“值得参考”是对写法的判断；工作经历、百分比和上线规模是作者自述，未做背景调查或重跑实验，也没有证据说明某份简历带来了录用。英文内容以下用中文概括，不全文翻译。

## 建议优先看的七份

### 1. Junshu Sha：中文工程表达，最适合参考结构

[公开中文简历](https://shaysha-pra.github.io/resume/)

相关项目为 My Company Brain。作者按知识链路、混合检索与引用、权限边界、自动化部署四点展开，写明关键词／字面／向量召回、RRF、资料过滤和引用粒度；将本地部署与测试结果单列。

借鉴：每条围绕一个工程问题组织，权限具体落实到查询边界。我们的增量入库、事务替换、授权快照和引用还原都适合这样写。无需照搬三套知识系统与大量服务；服务数量本身不是质量指标。

### 2. Dithob：中文业务场景与评测结合

[公开简历页](https://dithob.github.io/about/)

医药问答项目说明了采购、库存等业务场景，作者自述涉及 800 余张表、约 200 条评测样本，以及 SQL 执行成功率约 70% 到 90% 以上。正文明确自己是项目主要成员，并解释 Schema 检索、SQL 生成、预执行与错误回传。

借鉴：写出失败如何回到系统形成改进。需要注意 SQL 能执行不等于查询语义正确；我们同样不能把引用结构通过率当答案准确率。这个场景属于 RAG 与 Text-to-SQL 结合，和纯文档问答的指标不能直接横比。

### 3. Siddharth Nair：与我们最相近的文档 RAG 工程项目

[公开简历 PDF](https://www.siddharthnair.me/resume.pdf)

Monolith AI Assistant 将权限感知检索、混合召回、重排、相邻片段引用、异步文档队列和多租户后端分开介绍；作者列出 40 多个接口。

借鉴：介绍检索技术的同时说明权限和文档处理约束，展示系统如何运行。我们的服务端身份过滤、同一授权快照补全证据、版本替换，比单列框架名称更有辨识度。其 RAG 条目没有展示完整检索对照表；不能只因功能多就推断效果好。

### 4. Elambharathi Thangavel：工程优化写得具体

[公开简历 PDF](https://elambharathi.com/Portfolio/resume.pdf)

Bubble RAG 条目写两阶段检索和配置校验；作者另在 Jira Agent 条目中说明将 PyTorch 切换到 CPU 安装源，使镜像从 6 GB 缩至 800 MB。两个项目的数字归属清楚。

借鉴：一个具体故障或工程优化，比“完成 Docker 部署”更有解释空间。其分块从 322 个减至 82 个属于数量变化，不能单凭数量证明质量改善。我们应保留 MRR 对照和真实失败回归，不借用其镜像数据。

### 5. Deepak Silaych：应届背景下突出相对基线

[公开简历 PDF](https://deepaksilaych.me/resume.pdf)

FinSight 聚焦金融年报与表格问题，作者自述多跳检索相对普通 RAG 的准确率翻倍，表格查询模块提升 31%；同时说明 LangGraph、前后端及本人实现的模块。

借鉴：把“针对哪类问题、相对哪个基线”放在一条里。简历本页未给出完整样本量及评分协议，百分比只能视为作者声明。我们有固定 32 题、四模式、三轮对照，可以明确写 MRR@5 0.601 与 0.810，便于面试追问。

### 6. Sam Latino：评测工具也能成为项目亮点

[公开简历网页](https://samlatino.dev/resume/)

作者的开源项目包括 BM25 基准对比、工具调用失败分类、可恢复的重复评测以及回归检查。技术描述能够指出评测对象和验证办法。

借鉴：不要把所有评测缩成“测试通过”。我们可以写明无答案、错误前提、跨租户和伪造权限场景，以及固定快照、原始结果留存。它提供的是邻近的检索／Agent 工程参考，并非与我们的 RAG 完全相同。

### 7. Ahmed Doghri：只借鉴量化组织方式

[公开简历 PDF](https://adoghri.com/assets/pdf/ADoghri%20Resume.pdf)

作者为资深工程师，Slack RAG 条目同时交代混合检索与重排、引用评测、延迟和人工查询负担，分别自述引用精度 94%、延迟降低 35%、人工查询减少 50%。

借鉴：区分质量、性能和业务收益三类指标。该页未提供全部实验协议；这些生产经验也不应作为研究生实习项目的必达标准。我们没有真实用户查询负担数据，不应写节省人工百分比。

## 这次没有采用的材料

- 培训课程与“项目简历模板”：可以参考排版，但不能作为某位求职者的实际经历或成功录用证据。
- 有些项目仓库把评测数字留成 TBD，不适合作为有实测支撑的高质量案例。
- Akshay Patel 的搜索摘要包含旧版延迟／召回数字，当前打开的 PDF 只保留混合检索介绍；不把旧摘要数字说成当前正文内容。
- Mayur Jadhav、Raghav Upadhyay 的候选 PDF 链接本次返回 404，未纳入精选。
- Justin Liu 的 RAG 条目只简述文章树检索，缺少基线和测量细节，因此没有作为重点写法样本。

## 适合我们采用的四条简历表述

**研发／运维文档知识库问答系统｜Python、FastAPI、SQLite、BM25、RRF、ONNX**

基于开源 rag-qa-system 改造，围绕文档更新、资料权限、答案引用与检索评测完善研发知识库问答链路。

- 实现带来源、行号与版本的文档入库，使用内容摘要跳过重复处理、SQLite 事务替换旧版本片段；检索前按服务端身份过滤租户与部门权限。
- 在固定 32 题开发集上对向量、BM25、混合召回及重排进行三轮对照，纯向量与混合重排的 MRR@5 分别为 **0.601、0.810**，记录召回覆盖与 CPU 耗时代价。
- 针对引用格式失真和答案缺少代码步骤，将模型复制原文改为选择片段编号并由服务端还原，在同一授权快照内补充相邻说明及代码；对原 7 个失败场景进行两轮真实模型回归，**14/14 达到既定预期**。
- 构建 **50 题端到端评测及 76 项自动化测试**，覆盖无答案、错误前提、权限边界、版本更新和异常恢复；完成 Linux ARM64 容器构建、持久化与重建验证。

技术贡献归属详见 [上游与本次改造](upstream-and-changes.md)：混合检索和重排由上游已有，本次重点是工程改造、失败修复与可复现评测。14/14 是历史针对已知问题的回归结果，不是整个系统语义准确率。

## 面试需要说明的真实边界

- 当前资料为 22 份／325 个片段，属于小规模公开技术文档知识库。
- 四模式排名指标对照不等于自研新算法；BM25 证据覆盖率 93.75%，高于混合重排的 89.06%，重排并非全面胜出。
- 50 题中 39 题回答、11 题合理拒答，自动动作／权限检查通过不等于语义全对。
- 本次 AI 辅助复核严格通过 47/50，三题范围表述需要修改；人工作者实际评分 3 题，独立第三方复核未完成。不要写“人工准确率 94%”。
- 本地 Linux 虚拟机里的容器验证不等于企业公网生产上线，未宣称真实用户规模或线上 SLA。
- 当前评测集参与过开发，尚缺独立留出集；中文辅助译文不等于完成全量中文检索评测。

根据这些公开材料作出的判断：我们已经有适合简历的工程点和量化对照，接下来应把描述压缩为四条，并能解释每个数字的样本和限制。这个判断不代表对北京招聘通过率的统计预测。
